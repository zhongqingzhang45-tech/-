# Decision Log · 决策记录（ADR）

> 本文档记录所有架构 / 产品 / 设计层面的重要决策。
> **任何已记录的 ADR 禁止被推翻**，除非走「宪法修改」流程（见 AGENTS.md §10）并在本文档追加新 ADR 显式废弃旧 ADR。
>
> ADR 编号单调递增，不回收。状态：`Accepted` / `Superseded by ADR-XXX` / `Deprecated`。

---

## ADR-001 · 采用 AIRI 作为身体层

- **状态**：Accepted
- **日期**：v0.1 MVP
- **决定**：以 AIRI 开源项目作为 Live2D / Voice / Animation / Chat 的身体层，二次开发仅通过扩展点接入。

- **原因**：
  - AIRI 已具备成熟 Live2D 渲染、语音、动作能力。
  - 自研将消耗大量时间且难以达到同等质量。
  - 扩展架构允许快速迭代灵魂层而不破坏身体层稳定性。

- **禁止**：
  - ❌ 重新开发角色渲染系统。
  - ❌ 修改 AIRI 核心源码。

- **后果**：
  - 灵魂层必须以事件 / 扩展点方式接入 AIRI，不能直接操作 Canvas。
  - 升级 AIRI 时需评估扩展点兼容性。

## ADR-002 · UI 采用数字生命空间风格

- **状态**：Accepted
- **日期**：v0.1 MVP
- **决定**：所有 UI 采用 `Anime + Future + Emotional + Digital Life` 风格，主色星河粉紫 + 深海青蓝，深色沉浸背景。

- **原因**：
  - 产品定位是「数字生命」，不是工具。
  - 后台管理 / 廉价 AI 工具视觉会破坏沉浸感与情感连接。
  - 用户感知「她在」是核心体验。

- **禁止**：
  - ❌ 后台管理 Dashboard 视觉。
  - ❌ 普通白色企业后台配色。
  - ❌ 默认组件库样式直接出货。
  - ❌ 表格 / 进度条直白展示情感。

- **后果**：
  - 每个 UI 改动需对照 `docs/design-system.md` 自检。
  - 视觉资源投入高于普通业务系统。

## ADR-003 · 情绪必须驱动行为

- **状态**：Accepted
- **日期**：v0.1 MVP
- **决定**：情绪系统采用 PAD 模型（Pleasure / Arousal / Dominance），且情绪状态必须驱动 AI 回复、动作、Live2D 参数，最终影响用户感知。

- **原因**：
  - 仅显示情绪数字 / 标签无法产生生命感。
  - 闭环驱动才能让情绪「可见、可感、可影响关系」。

- **禁止**：
  - ❌ 只显示情绪状态。
  - ❌ 情绪与行为 / Live2D 参数脱节。

- **后果**：
  - 每个情绪变化必须产生可感知的下游影响。
  - Emotion Engine 必须与 Behavior / Live2D 紧耦合（通过事件）。

## ADR-004 · 记忆必须分层长期化

- **状态**：Accepted
- **日期**：v0.1 MVP
- **决定**：Memory Engine 必须实现分层长期记忆：

```
Short Term · Episodic · Emotional · Relationship · Identity
```

- **原因**：
  - 单纯保存聊天记录无法支撑「她记得你」的体验。
  - 不同记忆类型驱动不同行为（情节 vs 情绪 vs 身份）。

- **禁止**：
  - ❌ 只保存聊天记录。
  - ❌ 用单一上下文窗口模拟记忆。

- **后果**：
  - 需要向量库支持语义检索。
  - 记忆写入 / 检索必须有明确性能边界。

## ADR-005 · 关系是多维向量，非单一数值

- **状态**：Accepted
- **日期**：v0.1 MVP
- **决定**：Relationship Engine 不使用单一「好感度」数值，而是多维向量：信任 / 熟悉 / 依恋 / 互动历史。

- **原因**：
  - 单一数值无法表达关系的复杂性与张力。
  - 多维向量支持更细腻的行为响应（如「熟悉但缺乏信任」）。

- **禁止**：
  - ❌ `好感度 +1` 式简单加法。
  - ❌ 用进度条直白展示关系数值。

- **后果**：
  - 需要关系向量数据结构与演化算法。
  - UI 必须用关系图谱 / 距离 / 光强度等可视化方式呈现。

## ADR-006 · 灵魂层禁止直接操作 AIRI 核心

- **状态**：Accepted
- **日期**：v0.1 MVP
- **决定**：Life Runtime（灵魂层）只能通过 AIRI 暴露的扩展点（事件、参数注入、消息中间件）影响身体层，禁止直接调用 AIRI 内部 API 或操作 Canvas。

- **原因**：
  - 解耦灵魂与身体，便于独立演进与测试。
  - 保护 AIRI 升级路径。

- **禁止**：
  - ❌ 灵魂层直接操作 DOM / Canvas。
  - ❌ 在身体层实现情绪 / 记忆 / 关系逻辑。

- **后果**：
  - 必须有明确的事件总线 / 扩展契约。
  - 所有跨层通信走 `lib/core/live2d-manager.ts` 等适配层。

## ADR-007 · TypeScript Strict + 单文件 300 行上限

- **状态**：Accepted
- **日期**：v0.1 MVP
- **决定**：所有代码 TypeScript Strict；单文件不超过 300 行；DDD 模块化。

- **原因**：
  - 长期项目需要类型安全与可维护性。
  - AI 协作开发场景下，小文件更易审查与回滚。

- **禁止**：
  - ❌ 使用 `any`。
  - ❌ 单文件超过 300 行。
  - ❌ 跨子系统直接访问内部状态。

- **后果**：
  - 复杂逻辑必须拆分多文件。
  - 公共 API 必须有类型与 JSDoc。

## ADR-008 · 禁止引入新 UI 框架

- **状态**：Accepted
- **日期**：v0.1 MVP
- **决定**：UI 层不引入 Material UI / Ant Design / Chakra 等组件库，使用自研组件 + Glass Morphism 风格。

- **原因**：
  - 默认组件库样式与「数字生命空间」视觉冲突。
  - 自研可完全控制圆角 / 毛玻璃 / 微光等关键视觉。

- **禁止**：
  - ❌ 引入新 UI 框架。
  - ❌ 默认样式直接出货。

- **后果**：
  - 需要维护自研组件库。
  - 视觉规范需在 `design-system.md` 严格定义。

## ADR-009 · 不修改 AIRI 核心源码

- **状态**：Accepted
- **日期**：v0.1 MVP
- **决定**：AIRI 作为外部依赖引入，禁止修改其核心源码；所有定制能力通过扩展点实现。

- **原因**：
  - 保留 AIRI 升级路径。
  - 避免 fork 后维护成本爆炸。

- **禁止**：
  - ❌ 任何对 AIRI 仓库内文件的直接修改。
  - ❌ 为绕过限制而 monkey-patch AIRI 模块。

- **后果**：
  - 若 AIRI 缺失必要扩展点，需向上游提 issue / PR。
  - 临时绕过方案必须在本日志追加 ADR 说明。

## ADR-010 · Trae 开发前置流程强制化

- **状态**：Accepted
- **日期**：v0.1 MVP
- **决定**：Trae 每次开发前必须按 `AGENTS.md §0` 顺序阅读宪法与设计文档，输出开发计划并等待确认，禁止直接编码。

- **原因**：
  - AI 协作开发容易跳过架构思考直接产出代码。
  - 强制前置流程确保每次改动可追溯、可审查。

- **禁止**：
  - ❌ 跳过阅读直接写代码。
  - ❌ 跳过「开发计划」直接编码。
  - ❌ 跳过用户确认直接交付。

- **后果**：
  - 所有 AI 改动必须先有 Proposal。
  - 自检清单成为提交门槛。
